## Notes

Case 1 Tier 1 is still **not met**: memory per connection is 72.3 KiB against 64. Everything else passes.

- This run is after [ADR 0010](../decisions/0010-per-connection-memory.md): each session runs on its own goroutine, so net/http's request state can be collected, and the hijacked connection gets 1 KiB and 2 KiB buffers instead of 4 KiB each. Against [the run before it](2026-11-07-idle-t1.md): RSS per connection 84.1 → 72.3 KiB, heap and stacks per connection 57.0 → 42.3 KiB. Goroutines, CPU, bandwidth and tick time are unchanged.
- An exact heap profile at 1,000 idle connections (`GODEBUG=memprofilerate=1`) measured live heap at 18.6 KB per connection before and 10.0 KB after. Goroutine stacks are about 10 KiB per connection, with or without `GODEBUG=adaptivestackstart=0`.
- What's left is mostly runtime slack, not per-connection data. With `GODEBUG=gctrace=1`, 100 idle connections leave about 1 MB of live heap after a collection, below Go's 4 MB minimum GC goal. Memory freed after the handshakes stays mapped until the scavenger returns it, and (RSS − baseline) / 100 counts that as about 30 KiB per connection. At 1,000 connections the same slack is spread ten times thinner.
- Next: the GC settings ADR (BUILD.md 3.5). Separately, the owner may decide whether Tier 1 should subtract a fixed runtime floor (see ADR 0010).
